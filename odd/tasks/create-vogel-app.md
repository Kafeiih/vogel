# Feature: create-vogel-app
Objective: a Go CLI (`go run github.com/kafeiih/vogel/cmd/create-vogel-app@vX.Y.Z <name>`) that creates a new standalone service repo from examples/boilerplate, asking which optional components to keep.
Branch: feat/create-vogel-app (base master 3660fe2). Delivery: stacked-to-main, PRs per work unit. Test runner: go test (root module), plus generated-output build/test in vogel CI.

## Specs
- S1 (user, L1): "lo que haremos es crear algun tipo de script que podamos ejecutar y que copie el boileplate, de esta manera quiero crear un comando que cree un nuevo proyecto como create-next-app". A command that creates a new project from the boilerplate.
- S2 (user, L2): "cuando haga el create-vogel-app ahi debe formatear la iamgen con los nombres correspondientes preguntarme si usare worker, cerbos, algun otro cmd, etc. y la publicación se hara en ese nuevo repo que se solicitara crear." It asks which components to use and rewrites image names for the new repo; publishing happens from the new repo (the template release workflow).
- S3 (user: "dale con la A", source): the CLI downloads the GitHub tarball of the vogel tag matching its own version (debug.ReadBuildInfo) and extracts examples/boilerplate; when run from a local checkout it uses the local directory instead (flag --from <dir>).
- S4 (user: "dale con A", GitHub): local only. It creates the directory, runs `git init` and a first commit, and prints the exact `gh repo create` command; it performs no remote action. Creating the repo automatically is a possible later addition.
- S5 (from the mapping): selectable components are worker (with notification as a sub-option, only meaningful with the worker), bundled Cerbos PDP (authorization code stays; without it the api targets an external TLS PDP), and S3 storage. Audit, authorization, Zitadel, metrics and Swagger are always included.
- S6 (assumption, conventions): interactive prompts when stdin is a TTY, plus flags for non-interactive use (--yes). Rewrites: module path; go.mod drops the replace and requires the CLI's vogel version, then `go mod tidy`; Dockerfile APP_DIR default `.`; compose build context and image names ghcr.io/<owner>/<repo>[-worker|-cerbos]; Makefile docker-build context; boilerplate_db / bluprint_dev / "Go Bluprint" names; vogel-only README sections. Generates a .gitignore and a CI workflow (lint, test, govulncheck, gitleaks, trivy). Minimum supported vogel version: the first tag after v0.9.0 (v0.9.0 lacks cerbos/ and .github/).
- Removal mechanism (design): component-marked blocks in the boilerplate (`vogel:component <name> begin` / `end` comment lines, in the comment syntax of each file) plus a per-component list of whole paths to delete. The CLI deletes deselected blocks and paths and strips every marker line. vogel CI generates every component combination and builds/tests the output.
