# Feature: boilerplate-cerbos-template
Objective: give examples/boilerplate a validated Cerbos policy bundle and a template release workflow that a generated project (future create-vogel-app) uses to publish its own GHCR images.
Branch: feat/boilerplate-cerbos-template (base master 8850106). Delivery: stacked-to-main, 2 PRs (PR1 = T1+T2+T5, PR2 = T3+T4). Test runner: go test, docker build (cerbos validate), actionlint, trivy config.

## Specs
- S1 (user, 2026-10-15): "quiero que traigar a este boiler: - politicas de cerbos y cerbos." Bring go-bluprint's Cerbos pieces (policies, policy tests, baked PDP image, test/smoke scripts) into examples/boilerplate. The policy must match the boilerplate's role matrix (rolematrix_test.go: audit:entry list -> admin; view -> admin, auditor), not go-bluprint's (which lets auditor list). The local dev Cerbos must serve these policies.
- S2 (user): "debe publicar imagenes" refined by "T3-T4 recuerda que es boilerplate no necesito primero que nada publicar una imagen del boilerplate, cuando haga el create-vogel-app ahi debe formatear la iamgen con los nombres correspondientes preguntarme si usare worker, cerbos, algun otro cmd, etc. y la publicación se hara en ese nuevo repo que se solicitara crear." vogel itself publishes NO boilerplate images. The boilerplate ships a template release workflow (inert inside vogel) that publishes api/worker/cerbos images to the generated repo's GHCR, names derived from the repo (no hardcoding), so create-vogel-app can drop components.
- S3 (user: "dale con la A"): the deploy compose runs Cerbos with no published ports on an internal network, and the api/worker set CERBOS_PLAINTEXT=true explicitly, documented.
- S4 (assumption, from the vogel conventions): pinned base images by digest, SHA-pinned actions, no :latest tags, non-root containers, trivy config HIGH/CRITICAL clean, CODEOWNERS and dependabot coverage for new Dockerfiles.
- Out of scope: create-vogel-app itself; a template ci.yaml for generated repos (noted for create-vogel-app).
